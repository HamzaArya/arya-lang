# Arya 0.2.0-alpha.1 — local preview

This local prerelease adds standard source maps and mapped CLI runtime stacks. The compiler API accepts `{filename, outputFilename}` and returns `{code, map, mapFilename, symbols, usesPython}`. The legacy filename call remains available.

`arya build` writes an adjacent `.mjs.map`. `arya run` enables Node source maps automatically. Standalone output needs `node --enable-source-maps generated.mjs`. AryaCode consumes the exact same archived package and enables the flag in its normal runner.

Tests cover original file/line/column, function caller frames, multiline expressions, `await`, Python/built-in failures, Unicode, spaces, distinct expressions on one line, map metadata, and containment.

M1 qualification now includes CLI Build followed by standalone Node execution, passive Check, syntax failures preserving previous code/map artifacts, and literal program arguments. The 16-test suite passes on macOS arm64 with Node 22.15.0 and 24.16.0; clean-installed package acceptance and five AryaCode integration tests also pass on Node 22.15.0 with Python 3.13.15. A Linux/Windows/macOS CI matrix is configured; Linux/Windows qualification remains pending. See [source-map acceptance](../source-maps.md).

The package remains private with inherited `UNLICENSED` metadata. Nothing has been published. The portable extension uses numeric version `0.2.0`, preview status, and `aryaLanguageVersion: 0.2.0-alpha.1` because VSIX versions do not use npm prerelease suffixes.

## M2 local update — 9 November 2026

The [normative 0.2 specification](../arya-specification.md) now defines the implemented core, including grammar/newline rules, precedence, scope timing, values/conversions, built-in errors, a guaranteed host-global list, exports, JavaScript import selection, Python transport, and limits. A shared internal host-global list prepares M3's resolver without changing the public compiler API. Approved M3 lexical checks and M4 module syntax/root rules are labeled unimplemented; neither feature is enabled by this documentation update.

Compatibility decisions preserve unary-before-power precedence (`-2 ** 2` remains `4`), block-scoped function hoisting, runtime temporal-dead-zone checks, operand-returning `and`/`or`, and nullish default-import fallback. For a library exporting null/undefined as its default, the alias remains its namespace and `alias.default` holds that value. No semantic migration is required for these decisions. The explicit host-global list is preparation for M3; other bare names still parse today, and will need a declaration, `globalThis` access, or an explicit import once lexical checks arrive.

Fixed numeric property access: `1.toString()` and normalized forms such as `1.0.toFixed(2)` previously emitted invalid JavaScript. They now execute as ordinary property calls. Existing workaround `(1).toString()` remains valid; rebuild generated modules to get the fix. No source rewrite is required.

The specification also records the existing runtime-scope limitation: module-level host-name shadowing can affect injected built-ins or cause early initialization errors. Inner-scope shadowing is unaffected. Conformance tests preserve and explain that limitation pending runtime isolation work.

Next: lexical checks, relative Arya module builds, interop hardening, and clean release qualification. See the [roadmap](../arya-roadmap.md).
